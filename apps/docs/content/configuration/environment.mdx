# Environment Variables

All configuration options for the Rustrak server.

## Required

| Variable | Description |
|----------|-------------|
| `DATABASE_URL` | Database connection string. **Optional for SQLite** (defaults to `sqlite:///data/rustrak.db`). Required for PostgreSQL. |

### DATABASE_URL

Rustrak supports two database backends selected at compile time.

**SQLite**:

```bash
# Relative file path
DATABASE_URL=sqlite://./rustrak.db

# Absolute path
DATABASE_URL=sqlite:///var/lib/rustrak/rustrak.db

# In-memory (for testing only — data lost on restart)
DATABASE_URL=sqlite::memory:
```

**PostgreSQL**:

```bash
# Format
postgres://username:password@host:port/database

# Examples
DATABASE_URL=postgres://rustrak:rustrak@localhost:5432/rustrak
DATABASE_URL=postgres://rustrak:rustrak@postgres:5432/rustrak  # Docker
DATABASE_URL=postgres://user:pass@host:5432/rustrak?sslmode=require  # With SSL
```

## Security

| Variable | Default | Description |
|----------|---------|-------------|
| `SSL_PROXY` | `false` | Set to `true` when behind HTTPS proxy (nginx, Cloudflare) |
| `SESSION_SECRET_KEY` | (random) | 64-character key for session encryption |

### SSL_PROXY

Set to `true` when running behind a reverse proxy that terminates SSL (nginx, Cloudflare, etc.). This enables secure cookies.

```bash
SSL_PROXY=true
```

**When `SSL_PROXY=true`:**
- Cookies are sent only over HTTPS (`Secure` flag enabled)
- `SESSION_SECRET_KEY` becomes **required**

### SESSION_SECRET_KEY

Generate with:
```bash
openssl rand -hex 32
```

- **Development**: Optional (a random key is used, sessions don't persist across restarts)
- **Production with `SSL_PROXY=true`**: Required

The key must be at least 64 characters, which is what `openssl rand -hex 32`
produces: the cookie key is a 256-bit signing key followed by a 256-bit
encryption key. Anything shorter is refused at startup with the length it
received, so `openssl rand -base64 32` (44 characters) will not do. Changing the
key invalidates every existing session.

## Server

| Variable | Default | Description |
|----------|---------|-------------|
| `HOST` | `0.0.0.0` | TCP bind address |
| `PORT` | `8080` | Server port |
| `RUST_LOG` | `info` | Log level (trace, debug, info, warn, error) |
| `RUSTRAK_LOG_TIMEZONE` | `UTC` | IANA timezone name for log timestamp display (e.g. `Asia/Shanghai`) |
| `PUBLIC_URL` | *(none)* | Public-facing URL used in DSN strings shown to users |

### HOST

The network interface the server listens on. The default (`0.0.0.0`) means "all interfaces" and is correct for Docker — you don't need to set it explicitly.

Only change this if you want to restrict access to a specific interface:

```bash
HOST=127.0.0.1  # loopback only — useful for local dev behind a local proxy
```

> **Docker note:** `HOST=0.0.0.0` is already the default. You don't need to include it in your `docker-compose.yml` or `.env`. If you set `HOST=127.0.0.1` inside a container, the port mapping won't work and the server will be unreachable.

### PUBLIC_URL

The URL that Rustrak embeds in DSN strings. Must include the scheme (`http://` or `https://`). Trailing slashes are stripped automatically.

```bash
# Production (behind reverse proxy)
PUBLIC_URL=https://api.yourcompany.com

# Self-hosted with custom port
PUBLIC_URL=http://192.168.1.10:9090
```

**Why this matters:** `HOST=0.0.0.0` is the TCP *bind* address — it means "listen on all interfaces." It is not a routable address. Without `PUBLIC_URL`, the DSN shown in the dashboard will contain `http://0.0.0.0:8080/...`, which your SDK cannot reach.

When unset, Rustrak falls back to `http://{HOST}:{PORT}` — fine for local development where `HOST` is `localhost` or `127.0.0.1`.

### RUSTRAK_LOG_TIMEZONE

Converts the timestamps in the server's process logs (stdout — HTTP requests, background workers, event digestion, everything under `RUST_LOG`) to a specific IANA timezone for easier correlation with logs from other systems.

```bash
RUSTRAK_LOG_TIMEZONE=Asia/Shanghai
```

Use an IANA zone name (e.g. `Asia/Shanghai`, `America/New_York`, `Europe/Madrid`), not a fixed UTC offset — this ensures daylight saving time is handled correctly for zones that observe it. If unset, or set to a name that isn't a recognized IANA zone, logs fall back to UTC and the server still starts normally (a warning is logged when the value is invalid).

**Scope:** this only affects how log lines are displayed. It does not change event or issue timestamps — those are always stored and returned as UTC by the database and the API, regardless of this setting.

## Storage

| Variable | Default | Description |
|----------|---------|-------------|
| `INGEST_DIR` | `/tmp/rustrak/ingest` | Temporary event storage |
| `SOURCEMAP_STORAGE_PATH` | `/data/sourcemaps` | Directory for source map chunk storage |
| `SOURCEMAP_CACHE_MB` | `64` | Memory kept for parsed source maps across events |

### SOURCEMAP_STORAGE_PATH

Where Rustrak stores source map chunks uploaded by Sentry SDKs. Chunks are stored in a content-addressable layout: a SHA-1 hash like `abc123...` is written to `{SOURCEMAP_STORAGE_PATH}/ab/c123....map`.

```bash
SOURCEMAP_STORAGE_PATH=/var/lib/rustrak/sourcemaps
```

**Storage sizing:** Each source map chunk is typically around 2MB. Multiply by the number of distinct source files across all your deployments. A typical JavaScript app with 50 source files uses around 100MB.

**Production / multi-server deployments:** All server instances must read and write from the same `SOURCEMAP_STORAGE_PATH`. Mount a shared volume (NFS, EFS, a network filesystem) and point every instance at it. Without this, chunks uploaded to one instance won't be visible to others during bundle assembly.

### SOURCEMAP_CACHE_MB

Once a source map has been read and parsed for one event, Rustrak keeps the parsed form in memory so the next event that hits the same file skips both steps. This budget caps that memory, measured as the size of the source map files it holds, and the least recently used map is dropped first. A map larger than the whole budget is never kept.

```bash
SOURCEMAP_CACHE_MB=64
```

The cache only saves the file read and the parse. Which file a `debug_id` points to is looked up in the database on every event, so a deleted or re-uploaded source map takes effect immediately. Size it to hold the maps your errors actually hit: a handful of large Next.js server bundles is usually enough, and the default covers a 15 MB map four times over.

## Email Alerts (SMTP)

Global SMTP settings for email notifications. Channels can override these.

| Variable | Default | Description |
|----------|---------|-------------|
| `SMTP_HOST` | - | SMTP server hostname |
| `SMTP_PORT` | `587` | SMTP port (587 for STARTTLS, 465 for SSL) |
| `SMTP_USERNAME` | - | SMTP username |
| `SMTP_PASSWORD` | - | SMTP password |
| `SMTP_FROM` | `alerts@rustrak.local` | Default sender address |

## Dashboard URL

| Variable | Default | Description |
|----------|---------|-------------|
| `DASHBOARD_URL` | `PUBLIC_URL` | Base URL for the issue links in notifications |

The server serves the dashboard itself, so the links follow `PUBLIC_URL` and
this needs no setting. Set it only when the dashboard is served from another
host than `PUBLIC_URL`, such as a `rustrak-ui` container. With neither set, the
links use the server's bind address.

## Bootstrap

| Variable | Description |
|----------|-------------|
| `CREATE_SUPERUSER` | Create admin user on startup (`email:password`) |

```bash
CREATE_SUPERUSER="admin@example.com:secure-password"
```

Only creates user if database is empty.

## Dashboard

| Variable | Default | Description |
|----------|---------|-------------|
| `RUSTRAK_DASHBOARD` | `on` | Whether to serve the dashboard at all. `off` keeps the server API-only |
| `RUSTRAK_DASHBOARD_DIR` | `./static` | Where the compiled dashboard lives, relative to the working directory or absolute |

### RUSTRAK_DASHBOARD

`off` keeps the dashboard unmounted even though the image carries a build.
This is for the deployment that runs the dashboard from
[another host](/configuration/production#dashboard-on-its-own-host) and wants
the machine holding the data to serve no frontend at all.

```bash
RUSTRAK_DASHBOARD=off
```

`on`, `off`, `true`, `false`, `1` and `0` are accepted. Anything else refuses
to start, deliberately: a typo that silently left the dashboard on would
expose a UI you meant to keep off the box.

### RUSTRAK_DASHBOARD_DIR

The dashboard is static files, and the server hands them out from `/`. This is
where it looks for them. The image already puts a build at `/app/static`, which
is what the default resolves to, so you do not normally set this.

**It is a path, not a switch.** The dashboard is mounted when the directory
actually holds an `index.html` and skipped when it does not, so an image built
without a dashboard behaves exactly as one always has. To keep a build that is
there from being served, use `RUSTRAK_DASHBOARD=off` above.

```bash
# Serve a dashboard you built and mounted yourself
RUSTRAK_DASHBOARD_DIR=/srv/rustrak-dashboard
```

**There is no API address to configure.** The browser loads the dashboard from
the server and calls the API on that same origin, so the two can never disagree
about where the other one is. That also means the session cookie is
first-party, and no CORS policy applies to the dashboard's own requests.

`RUSTRAK_API_URL` is not a server variable. It belongs to the optional
`rustrak/rustrak-ui` image, nginx serving the same bundle for a dashboard
hosted [on its own host](/configuration/production#dashboard-on-its-own-host),
and it names the server that image proxies the API to. `HOSTNAME`, which was
the old dashboard process's bind address, is gone.

### The update check

The dashboard compares the running server's version against the release feed
published on GitHub Pages, and shows a notice when a newer one exists. **That
request is now made by the browser rather than by a server process**, which is
the one consequence of serving the dashboard as static files worth knowing
about: the feed is fetched from each reader's browser, on their connection,
rather than once per hour from the instance.

Nothing about the instance is sent — the request is a plain `GET` for a public
JSON file, with no identifier, telemetry or usage data — and every failure is
silent: a blocked or unreachable feed simply means no notice appears. The
browser's own HTTP cache decides how often it is re-fetched.

It is switched off at build time rather than at runtime, because a static
bundle has no process to read an environment from:

```bash
VITE_RUSTRAK_VERSION_CHECK_ENABLED=false pnpm --filter @rustrak/dashboard build
```

For an installation that must make no outbound requests at all and does not
build its own image, blocking the host at the network is the reliable answer.

## Telemetry

| Variable | Default | Description |
|----------|---------|-------------|
| `RUSTRAK_TELEMETRY` | `on` | Anonymous usage report every 6 hours. `off` sends nothing |
| `DO_NOT_TRACK` | unset | `1` sends nothing either; the cross-tool convention |

Either variable on its own is enough to turn it off. What the report
contains, field by field, is on the [Telemetry](/configuration/telemetry)
page.

## Complete Example

### SQLite (development / personal)

```bash
# .env file (SQLite — image tag: latest)

# Required
DATABASE_URL=sqlite:///data/rustrak.db

# Server (the dashboard is served by this same process, from /)
PORT=8080
RUST_LOG=info
```

### PostgreSQL (production)

```bash
# .env file (PostgreSQL — image tag: postgres)

# Required
DATABASE_URL=postgres://rustrak:password@postgres:5432/rustrak

# Security (required for production behind HTTPS proxy)
SSL_PROXY=true
SESSION_SECRET_KEY=generate-your-own-with-openssl-rand-hex-32

# Server
PORT=8080
RUST_LOG=info
PUBLIC_URL=https://api.yourcompany.com

# Database Pool
DATABASE_MAX_CONNECTIONS=20

# Rate Limiting
MAX_EVENTS_PER_MINUTE=1000
MAX_EVENTS_PER_HOUR=10000

# Dashboard (only for the links inside notifications; the dashboard itself
# needs no configuration, it is served from / by this process)
DASHBOARD_URL=https://rustrak.yourcompany.com

# Email Alerts (optional - can also configure per-channel)
SMTP_HOST=smtp.yourcompany.com
SMTP_PORT=587
SMTP_USERNAME=alerts@yourcompany.com
SMTP_PASSWORD=your-smtp-password
SMTP_FROM=alerts@yourcompany.com
```
