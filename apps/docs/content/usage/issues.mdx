# Issues

Every error an SDK sends is an event. Rustrak groups events caused by the same bug into one issue, so a crash that happens 500 times is one row with a count of 500, not 500 rows.

Each issue has a short ID: the project slug in capitals and a number, such as `STOREFRONT-1`. Click it on the issue page to copy it.

## The issue list

Open a project to see its issues. The tabs split them by state: **Open**, **Resolved**, **Muted** and **All**.

The bar above the table searches the error type, message, transaction and culprit, ignoring case, and filters by any column (priority, assignee, level and so on), by environment or by release. Start typing and it suggests the keys and their values.

Select rows with the checkboxes to resolve, mute, assign or delete several issues at once. Deleting removes the issue and all its events, and cannot be undone.

## The issue page

Click an issue to open it. The page shows one event at a time, the latest first, and the arrows next to **Event N of M** move through the rest. For each event you get:

- **Highlights**: level, handled or not, transaction, URL, environment, release
- **Stack Trace**, with the source lines when the SDK sends them or a [source map](/usage/source-maps) or [debug file](/usage/debug-files) supplies them
- **Breadcrumbs**: what the app did before the error
- **Tags** and **Context**: user, browser, OS and whatever your code added
- **Event Details** and the **Raw JSON** as the SDK sent it

The sidebar holds what belongs to the issue rather than to one event: status, priority, assignee, event and user counts, the release where it was first and last seen, tag breakdowns, the linked [GitHub](/configuration/github) issue, and an **Activity** feed where your team can leave comments.

## Resolve, mute, reopen

| Action | Shortcut | What happens |
|---|---|---|
| **Resolve** | `R` | The issue moves to **Resolved**. A new event reopens it as **Regressed**. |
| **Resolve in next release** | | Stays resolved while events keep arriving from the release it was resolved in. An event from a newer release reopens it. Events with no release count as the same release. |
| **Archive** | `E` | The issue moves to **Muted**. It keeps counting events but sends no alerts and never reopens on its own. **Unarchive** brings it back. |

**Resolve in next release** is under the arrow next to **Resolve**.

The issue page has more shortcuts: `B` bookmarks the issue, `I` assigns it to you, `Shift+C` copies its link.

## Priority

A new issue takes its priority from the event's level: `fatal` and `error` are **High**, `warning` is **Medium**, `info` and `debug` are **Low**, anything else is **Medium**. Change it from the sidebar; your choice sticks.

## How grouping works

Two events land in the same issue when they get the same grouping key. By default the key is the exception's type and message, for every exception in a chained error, plus the transaction name. An event without an exception uses its message instead.

Before comparing messages, Rustrak replaces the parts that change from one occurrence to the next (numbers, dates, hex values, UUIDs and similar) with placeholders. `Order 1234 not found` and `Order 5678 not found` are one issue. The issue title keeps the real text.

The stack trace does not take part. The same error thrown from two places is one issue; two different errors from the same line are two.

## Custom fingerprints

To group differently, set a fingerprint in the SDK. Events with the same fingerprint share an issue, whatever their message:

```javascript
Sentry.captureException(error, {
  fingerprint: ['payment-gateway-timeout'],
});
```

`{{ default }}` stands for the default grouping key, so you can split an issue further instead of replacing the key:

```javascript
Sentry.captureException(error, {
  fingerprint: ['{{ default }}', region],
});
```

`{{ default }}` is the only variable Rustrak understands. Sentry's `{{ transaction }}`, `{{ type }}` and the rest are taken as literal text, so pass the value yourself instead. An empty fingerprint falls back to default grouping.

Fingerprints only affect events sent after you add them. Issues that already exist keep their events.
