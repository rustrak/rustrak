# Issues

Every error an SDK sends is an event. Rustrak groups events caused by the same bug into one issue, so a crash that happens 500 times is one row with a count of 500, not 500 rows.

Each issue has a short ID: the project slug in capitals and a number, such as `STOREFRONT-1`. Click it on the issue page to copy it.

## The issue list

Open a project to see its issues. The tabs split them by state: **Open**, **Resolved**, **Archived** and **All**.

The bar above the table searches the error type, message, transaction and culprit, ignoring case, and filters by any column (priority, assignee, level and so on), by environment or by release. Start typing and it suggests the keys and their values.

<InteractiveDemo src="/demos/issues.openshowcase" />

Select rows with the checkboxes to resolve, archive, assign or delete several issues at once. Deleting removes the issue and all its events, and cannot be undone.

## Every project at once

**Issues** in the sidebar, above your projects, lists the open issues of every project in one table. It is the page to check when one product is split across several projects (a web app, its API, a mobile app) and you want to know what broke today without opening each one.

Two tabs split the page:

- **Errors**: the open issues, newest activity first.
- **Feedback**: the [user feedback](/usage/user-feedback) still in the inbox, with the same reading pane as a project's **User Feedback**.

Each tab shows how many are waiting. The project picker at the top right narrows both tabs to the projects you tick, and keeps them when you switch tab. With nothing ticked, the page covers **All projects**: every project you can read issues on. The picker offers your first 100 projects.

<InteractiveDemo src="/demos/issues-all.openshowcase" />

The table is the project issue list with one more column, **Project**, which shows each issue's project and its platform logo. The search bar and the column filters work the same, except that environment and release suggest no values: type `environment:production` and press Enter. Click a row to open the issue in its project.

Ticked rows can come from different projects: resolving, archiving, setting the priority or deleting them sends one request to each project. Assigning across projects only offers **Assign to me** and **Unassign**, since each project has its own members.

Resolved and archived issues are not listed here, and neither is feedback you resolved or marked as spam. To go through those, open the project.

You only see the projects where you can read issues. A project you have no access to is left out, with no error, so the page never tells you it exists.

### From the API

The same lists are two endpoints. `project` takes comma-separated project IDs. Without it you get every project the token can read:

```bash
curl -H "Authorization: Bearer $RUSTRAK_TOKEN" \
  "$RUSTRAK_URL/api/issues?project=1,2&filter=open"
curl -H "Authorization: Bearer $RUSTRAK_TOKEN" \
  "$RUSTRAK_URL/api/feedback?project=3"
```

Each issue in the response carries its `project_id`. The other parameters are the project list's (`filter`, `q`, `sort`, `page` and so on), listed in the [API reference](/api-reference).

Tools built for Sentry can use Sentry's organization endpoint, `GET /api/0/organizations/{org}/issues/`. It takes `project` repeated, Sentry's way (`?project=1&project=2`), and `project=-1` or no `project` means every project. Rustrak has one organization, so `{org}` can be anything.

## The issue page

Click an issue to open it. The page shows one event at a time, the latest first, and the arrows next to **Event N of M** move through the rest. For each event you get:

- **Highlights**: level, handled or not, transaction, URL, environment, release
- **Stack Trace**, with the source lines when the SDK sends them or a [source map](/usage/source-maps) or [debug file](/usage/debug-files) supplies them
- **Breadcrumbs**: what the app did before the error
- **Tags** and **Context**: user, browser, OS and whatever your code added
- **Event Details** and the **Raw JSON** as the SDK sent it

The sidebar holds what belongs to the issue rather than to one event: status, priority, assignee, event and user counts, the release where it was first and last seen, tag breakdowns, the linked [GitHub](/configuration/github) issue, and an **Activity** feed where your team can leave comments.

## Resolve, archive, reopen

| Action | Shortcut | What happens |
|---|---|---|
| **Resolve** | `R` | The issue moves to **Resolved**. A new event reopens it as **Regressed**. |
| **Resolve in next release** | | Stays resolved while events keep arriving from the release it was resolved in. An event from any other release reopens it, an older one included. Events with no release count as the same release. Creating a newer release through the API ends the wait, so from then on any event reopens it. |
| **Archive** | `E` | The issue moves to **Archived**. It keeps counting events but sends no alerts and never reopens on its own. **Unarchive** brings it back. |

**Resolve in next release** is under the arrow next to **Resolve**.

<InteractiveDemo src="/demos/issues-archive.openshowcase" />

The issue page has more shortcuts: `B` bookmarks the issue, `I` assigns it to you, `Shift+C` copies its link.

## Priority

A new issue takes its priority from the event's level: `fatal` and `error` are **High**, `warning` is **Medium**, `info` and `debug` are **Low**, anything else is **Medium**. Change it from the sidebar; your choice sticks.

## How grouping works

Two events land in the same issue when they get the same grouping key. By default the key is the exception's type and message, for every exception in a chained error, plus the transaction name. An event without an exception uses its message instead.

Before comparing messages, Rustrak replaces the parts that change from one occurrence to the next (numbers, dates, hex values, UUIDs and similar) with placeholders. `Order 1234 not found` and `Order 5678 not found` are one issue. The issue title keeps the real text.

The stack trace does not take part. The same error thrown from two places is one issue; two different errors from the same line are two.

## Custom fingerprints

To group differently, set a fingerprint in the SDK. Events with the same fingerprint share an issue, whatever their message:

```javascript
Sentry.captureException(error, {
  fingerprint: ['payment-gateway-timeout'],
});
```

`{{ default }}` stands for the default grouping key, so you can split an issue further instead of replacing the key:

```javascript
Sentry.captureException(error, {
  fingerprint: ['{{ default }}', region],
});
```

`{{ default }}` is the only variable Rustrak understands. Sentry's `{{ transaction }}`, `{{ type }}` and the rest are taken as literal text, so pass the value yourself instead. An empty fingerprint falls back to default grouping.

Fingerprints only affect events sent after you add them. Issues that already exist keep their events.
