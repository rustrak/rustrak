# Storage

Every error, transaction, log and source map takes disk space. **Settings → Storage** shows what the instance holds, sets how long each kind of data is kept, and deletes old data. Only instance admins see it, since every cleanup deletes for good.

## Usage

- **Storage used**: the total, one bar split by kind (errors, transactions, logs, source maps) with what each weighs and how many rows or files it is, and a line saying when the next cleanup runs and roughly how much it frees.
- **Age of the data**: bytes by how long ago they arrived (under 7 days, 7–14, 14–30, 30–90, 90–180, 180 days to a year, over a year), stacked by kind. What the next cleanup deletes is hatched.
- **Projects**: what each one holds, largest first, its size per kind, and whether it uses the general retention or its own.

Sizes of errors, transactions and logs are the length of the payloads Rustrak holds, estimated from a sample of each project's rows and scaled by how many it has, so the page stays fast however much data there is: the newest rows for errors, transactions and logs, and for spans a random sample of the project's transactions. Source-map sizes are exact, summed from the stored file sizes. Row counts are exact, except spans, which are estimated from that sample. Ages are keyed on **ingestion time** (when Rustrak received the data), not on the client-supplied timestamp, like retention itself.

## Retention

- **Configure retention**, at the top of the page, sets how long each kind is kept in every project (7, 14, 30, 90, 180 or 365 days, or **Forever**) and when the cleanup runs: every day or every week, at an hour, in UTC. Everything is kept forever until you choose otherwise, and the cleanup only runs while some kind has a limit.
- **Change**, on a project's row, gives that project its own periods, or puts it back on the general ones.

Both say what the next cleanup would delete with your changes before you save. **Save** applies them at the next cleanup; **Save and clean up now** asks once more, with the size, and deletes in the background straight away.

### Deleting now

**Delete data now**, beside **Configure retention**, deletes without waiting for the cleanup: pick the kinds (errors, transactions, logs), how old (older than 1 to 365 days) and where (every project or one). The dialog counts what goes as you choose, and the button says how much. It runs in the background like the cleanup, and only one of them runs at a time. It can also delete the source maps no upload uses. If the server restarts while it runs, what it already deleted stays deleted, but nothing picks the rest up: run it again (the cleanup, by contrast, finishes the rest on its next run).

What a cleanup does:

- Deletes **events**, **transactions** (their **spans** go with them) and **logs** older than each project's period for that kind.
- Removes any **issue** left with zero events, and keeps the event counts on projects and issues in sync.
- Deletes the **source maps no upload references** any more, for example the ones a deleted project left behind. Referenced files are never touched.
- Works in small batches, each committed on its own, so ingestion keeps working. If the server restarts mid-cleanup, what was already deleted stays deleted and the next run finishes the rest. If the server was down at run time, it runs once when it comes back.
- On SQLite, gives the space it freed back to the disk once the deletes are done, a few megabytes at a time, so the database file shrinks. This needs a database Rustrak created with incremental auto-vacuum, which every new one is; an older file reuses the freed space for new data but keeps its size until it is compacted once, with the **Compact database** button on this page (see [Reclaiming disk space](/configuration/database#reclaiming-disk-space)). Compaction needs free disk space about the size of the database and blocks writes while it runs: errors that arrive meanwhile are kept and processed afterwards, but logs, traces and sessions are lost. Run it at a quiet time.

> **Warning:** Deleted data is gone for good. Check what the panel says will go before you save.

## API access

Every endpoint requires an **admin** bearer token (or admin session). Non-admins get `403 Forbidden`.

```bash
# Instance-wide summary
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/summary

# Per-project breakdown
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/projects

# Dry-run a cleanup (deletes nothing)
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"older_than_days":30}' \
  http://localhost:8080/api/storage/cleanup/preview

# Start the cleanup (optionally scoped to one project). Answers 202 at once.
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"older_than_days":30,"project_id":1}' \
  http://localhost:8080/api/storage/cleanup

# Follow it until it is no longer "running"
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/cleanup/status

# How long ago each project's data arrived, per kind
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/age

# Enforce the saved retention now (202, then follow the cleanup status)
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/retention/run

# Retention: read it, see what new settings would delete, save them.
# A null period keeps that kind forever; an override replaces the defaults
# for its project.
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/retention
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"defaults": {"events_days": 90, "transactions_days": 30, "logs_days": 14},
       "overrides": [{"project_id": 1, "events_days": 365, "transactions_days": null, "logs_days": 7}],
       "frequency": "daily", "hour": 3, "weekday": 0}' \
  http://localhost:8080/api/storage/retention/preview
curl -X PUT -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"defaults": {"events_days": 90, "transactions_days": 30, "logs_days": 14},
       "overrides": [], "frequency": "weekly", "hour": 4, "weekday": 0}' \
  http://localhost:8080/api/storage/retention

# Dry-run, then remove, orphaned source maps
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/source-maps/gc/preview
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  http://localhost:8080/api/storage/source-maps/gc
```

The preview returns the counts a cleanup would remove:

```json
{ "events": 1240, "transactions": 80000, "spans": 1200000, "logs": 5000, "issues_removed": 37 }
```

Starting a cleanup and asking for its status both return the job. `state` is `idle` (none since the server started), `running`, `completed` or `failed`, and `removed` has the same shape as the preview: the rows deleted so far while it runs, the total once it has finished.

```json
{
  "state": "completed",
  "removed": { "events": 1240, "transactions": 80000, "spans": 1200000, "logs": 5000, "issues_removed": 37 },
  "started_at": "2026-10-07T10:00:00Z",
  "finished_at": "2026-10-07T10:04:12Z",
  "error": null
}
```

You can also drive all of this from an AI assistant via the [MCP server](/sdks/mcp): the cleanup tool, and saving retention that deletes anything, both require an explicit confirmation flag.

## Behavior reference

| Situation | Result |
|---|---|
| Member opens **Settings → Storage** or calls a storage endpoint | `403 Forbidden` |
| Preview (cleanup or source-map GC) | Counts only; nothing is deleted |
| Start a cleanup | `202 Accepted`; it runs in the background |
| Start a cleanup while one is running | `409 Conflict` |
| Server restarts during a cleanup | Batches already deleted stay deleted; run it again for the rest |
| Cleanup scoped to one project | Other projects' data is never touched |
| Every kind kept forever, by default and in every override | The cleanup never runs |
| Project with an override | Its own periods apply; the defaults don't |
| Issue left with zero events after cleanup | Issue is deleted |
| Source-map GC | Only unreferenced (orphaned) files are removed |
| Deleting events | Project and issue event counts stay consistent |
| Cleanup on SQLite | The freed space goes back to the disk (a database created before incremental auto-vacuum needs a one-off `VACUUM` first) |
