# Team & Access

Rustrak supports multiple users on a single instance, with role-based access control over actions and projects. Invite teammates, give them their own login, and scope what they can see and do.

## Roles

There are two layers of roles.

### Global role

Every user has one global role:

- **Admin** — full access to every project plus team management (invite/remove users, change roles).
- **Member** — can only see and act on projects they are explicitly added to.

The **primary user** (the first account, created during bootstrap) is special: it can never be demoted or deleted, so an instance can't be locked out.

### Per-project role

Members are granted access to individual projects with a per-project role:

| Role | Can do |
|---|---|
| **Viewer** | Read issues, events, and project details |
| **Editor** | Everything a viewer can, plus resolve/mute/delete issues and update the project |
| **Admin** | Everything an editor can, plus delete the project and manage its members |

Global admins implicitly have full access to every project, so they don't need explicit membership.

## Inviting people

Registration is **invite-only** — there is no open sign-up. Only admins can invite.

1. Go to **Settings → Team**
2. Under **Invite a member**, enter an email, pick a global role, and optionally turn on **Send invite by email**
3. Click **Invite** — the invite link is copied to your clipboard either way

By default no email is sent and you **share the link yourself** (chat, email, etc.). If email delivery is configured (see below), you can flip on **Send invite by email**: the invitation lands in the invitee's inbox with the link, the inviting admin's address, the granted role, and the expiry time. The link is still copied to your clipboard as a fallback, and the pending-invitations list shows whether each invitation was delivered — undelivered ones get a **resend** button.

Invitation links expire after 48 hours and can only be used once.

### Email delivery

The **Send invite by email** switch is only usable when a mail transport is configured. Two sources work, in this order of preference:

1. **An email alert integration** — any enabled email integration under **Settings → Alerts** carries its own SMTP settings (host, port, username, password, from address). The first enabled one is used.
2. **Server environment variables** — `SMTP_HOST`, `SMTP_PORT` (defaults to 587; port 465 uses implicit TLS), `SMTP_USERNAME`, `SMTP_PASSWORD` and `SMTP_FROM`.

If neither is configured the switch is greyed out. An emailed link is built from `DASHBOARD_URL` or `PUBLIC_URL`; with neither set and the server bound to a wildcard address (`0.0.0.0`) the link would point somewhere the recipient cannot open, so `send_email` requests are rejected until one of the two is set. Sending is best-effort: if the mail server rejects the invitation email, the invitation is still created (marked "not sent") and you can copy the link manually or hit resend later — an explicit resend, however, fails loudly if the mail server is unreachable.

### Accepting an invitation

The invitee opens the link (`/invite/<token>`), sets a password, and is logged in — their email and global role come from the invitation.

## Managing the team

From **Settings → Team** (admins only) you can:

- **Change a user's global role** between admin and member
- **Remove a user** — this revokes their access and tokens (with a confirmation step)

You cannot remove yourself, the primary user, or the last remaining admin.

## Managing project members

Open a project and use **Members** to control who can access it:

- **Add a member** — pick a user and a per-project role (viewer/editor/admin)
- **Change a member's role**
- **Remove a member**

The last admin of a project cannot be removed. When a member creates a project, they automatically become its admin.

## API access and tokens

API tokens are scoped to the user who created them — a token inherits that user's projects and permissions. See [API Tokens](/usage/tokens).

Admins can manage the team over the API too:

```bash
# List the team (admin token required)
curl -H "Authorization: Bearer YOUR_TOKEN" \
  http://localhost:8080/api/team

# Invite a member — returns a single-use invite token
curl -X POST -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"email":"teammate@example.com","role":"member"}' \
  http://localhost:8080/api/invitations

# Same, but also email the invite (requires configured SMTP — 400 otherwise)
curl -X POST -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"email":"teammate2@example.com","role":"member","send_email":true}' \
  http://localhost:8080/api/invitations

# Whether email delivery is available, and where it would come from
curl -H "Authorization: Bearer YOUR_TOKEN" \
  http://localhost:8080/api/invitations/email-status

# Re-send an undelivered invitation email (add "force":true to re-send a delivered one)
curl -X POST -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"force":false}' \
  http://localhost:8080/api/invitations/TOKEN/resend

# Add a user to a project as an editor
curl -X PUT -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"user_id":2,"role":"editor"}' \
  http://localhost:8080/api/projects/1/members
```

You can also manage all of this from an AI assistant via the [MCP server](/sdks/mcp).

## Behavior reference

| Situation | Result |
|---|---|
| Member opens a project they don't belong to | `404 Not Found` (existence is not leaked) |
| Viewer tries to resolve/delete an issue | `403 Forbidden` |
| Non-admin calls a team or invitation endpoint | `403 Forbidden` |
| `POST /auth/register` (open sign-up) | `403 Forbidden` — invite-only |
| `send_email: true` with no SMTP configured | `400 Bad Request` — the `send_email` field is named in `error.fields` |
| Resend for an expired or already-accepted invitation | `400 Bad Request` |
| Remove the last admin of an instance or project | `409 Conflict` |
